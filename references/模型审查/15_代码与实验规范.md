# 代码与实验规范

## 1. 推荐项目结构

```text
project/
├─ README.md
├─ data/
│  ├─ raw/          # 只读原始数据
│  ├─ interim/
│  └─ processed/
├─ src/
│  ├─ data/
│  ├─ features/
│  ├─ models/
│  ├─ evaluation/
│  └─ visualization/
├─ configs/
├─ notebooks/
├─ tests/
├─ outputs/
│  ├─ figures/
│  ├─ tables/
│  ├─ models/
│  └─ logs/
└─ report/
```

原始数据永不手工覆盖；所有中间结果应能由代码再生。

## 2. 可复现信息

记录：

- 操作系统、语言和依赖版本；
- 数据文件哈希或版本；
- 随机种子；
- 参数配置；
- 运行命令；
- 开始/结束时间；
- git commit（如有）；
- 求解器版本与状态；
- 硬件（对深度学习或大型优化重要）。

## 3. 随机性

统一管理种子，覆盖：

- Python/NumPy；
- 机器学习框架；
- 数据划分；
- 初始化；
- 元启发式；
- 仿真。

存在随机环节时，固定种子用于复现，多种子用于评估对随机性的敏感程度；报告种子集合、预算、波动与失败情况，有限种子测试不是稳定性的普遍证明。完全确定性的流程说明没有随机环节，不补造种子或无作用的重复运行。

## 4. 数据管道

- 读取后立即验证 schema；
- 显式解析日期、类别和缺失；
- 单位转换写成函数；
- 清洗前后记录行列数；
- 每个删除规则输出数量；
- 训练与预测共用同一预处理管道；
- 变换器只在训练数据拟合；
- 特征列顺序和类别映射随模型保存。

## 5. 函数设计

函数尽量：

- 单一职责；
- 输入输出明确；
- 不依赖隐藏全局变量；
- 可注入参数；
- 有类型/维度/单位说明；
- 对边界输入有测试。

模型、评估和绘图分开，避免一个 notebook 单元完成所有工作。

## 6. 实验配置

将可变参数放在配置文件，而不是散落代码：

- 数据路径；
- 划分日期；
- 特征集合；
- 模型参数；
- 优化容差；
- 随机种子；
- 输出目录。

每次实验保存配置副本与结果。

## 7. 结果表

建议每行一个实验，至少包含：

| run_id | data_version | model | params | seed | split | metric | value | runtime | status |
|---|---|---|---|---:|---|---|---:|---:|---|

不要手工把控制台最优值复制进论文；由脚本导出最终表图。

### 7.1 单一结果注册表

多步骤项目应维护一份机器可读的结果注册表，每个进入论文的主张至少包含：

| result_key | value | unit | scope | run_id | source_artifact |
|---|---:|---|---|---|---|
| 示例键 | 待运行生成 | 明确单位 | 数据、年份与情景 | 当前运行编号 | 输出表或审计记录 |

- 摘要、正文、结论、表格和图注从同一 `result_key` 取值，避免手工复制和局部四舍五入产生冲突；
- 同一指标的点估计、区间、情景和验证折使用不同键，不靠相近名称区分；
- 交付校验必须扫描一个结果键的所有展示位置。只断言“正确值至少出现一次”不能排除旧值仍留在其他段落；
- 文件改名后同步更新产物清单和验证入口。关键文件不存在时应失败，不得用“若存在则检查”静默跳过；
- 表图生成脚本、论文源码和最终 PDF 保存同一个 `run_id` 或清单哈希，以便确认它们来自同一轮结果。

本库提供[契约与文本数字审计](../../scripts/audit_contract.py)，具体声明和调用见[工程工作流](../论文与交付/交付审计.md)。它逐一比较绑定的实际展示值，并核对预期出现次数，避免某处正确而另一处仍旧，或删除标记后静默减少覆盖。当前数值来源适配JSON；既有Excel/CSV工程保留原主源，需要接入时由只读导出生成可追溯索引，不手工维护第二份数值。未绑定的正文、单位语义、PDF和图像仍须审阅，不能用机械PASS代替。

## 8. 数值检查

- NaN/Inf；
- 量纲和数量级；
- 矩阵维度；
- 概率和为 1；
- 决策变量边界；
- 约束违反量；
- 梯度/差分；
- 步长/网格收敛；
- 优化状态和 gap；
- 残差与预测区间。

## 9. 最小测试

- 数据读取 smoke test；
- 一个手算小例；
- 极端输入；
- 空数据/单行/常数列；
- 非负/守恒/单调等不变量；
- 固定种子结果；
- 输出文件存在且字段完整。

## 10. Notebook 规范

Notebook 适合探索，不应是唯一交付：

- 从上到下可运行；
- 清除无关输出；
- 不依赖手工执行顺序；
- 大逻辑下沉到 `src/`；
- 写明数据与环境；
- 最终图表由稳定脚本生成。

## 11. 图表输出

- 矢量优先用于线图/公式图，位图保证足够 DPI；
- 文件名包含内容而非 `figure1_final2`；
- 图的字号与论文版面匹配；
- 颜色、尺寸、字体统一；
- 生成图时同步导出绘图数据。

## 12. 交付前运行

1. 在干净环境安装依赖；
2. 从原始数据运行完整管道；
3. 核对关键数字与论文；
4. 检查无绝对私人路径；
5. 删除密钥和隐私数据；
6. 打包 README、依赖、配置、代码和必要数据；
7. 保存运行日志。

## 13. 国赛 AI 辅助过程记录

2026 年国赛允许使用 AI 工具，但要求公开透明、参赛队主导核心建模与分析，并对 AI 参与内容
逐项人工审查与核实。只要 AI 参与代码补全、调试、模型分析或其他实质环节，实验记录至少增加：

| 字段 | 应记录内容 |
|---|---|
| 工具 | 名称、版本或型号、访问日期 |
| 环节 | 对应题目、文件、函数、公式或写作段落 |
| 目的 | 语言润色、代码调试、候选模型、验证设计等具体用途 |
| 过程 | 主要提示方式、关键交互或可复查的过程摘要 |
| 采纳 | 哪些输出采用、拒绝或人工改写 |
| 核验 | 手算小例、单元测试、基线、独立来源、边界/不变量或复现实验 |
| 追踪 | 最终论文、代码提交和结果表中的对应位置 |

运行成功不等于已经完成必要人工核验；模型定义、公式条件、数据口径和关键结论仍按本库的证据门禁
逐项检查。参赛交付时，把上述记录整理为支撑材料中的 `AI工具使用详情.pdf`，并确保论文参考文献
之前的声明与记录一致。可从 AI 工具使用详情模板（扩展资料未随包提供） 起草，但不得赛后凭空
补造提示词、交互过程、采纳情况或核验结果。官方规则自 2026-09-01 起试行，提交前重新检查最新版本。

## 14. 2027 MCM/ICM 代码交付边界

COMAP 当前 2027 官方规则把代码计入 25 页总页数，并要求整份解决方案只交一个小于 25MB 的
PDF；不得另交程序、软件、数据库或其他文件。因此：

- 论文内只放支持复核所必需的关键伪代码、算法步骤或短代码片段，且全部计入 25 页；
- 不得因为官方不接收源文件，就省略本地完整工程、环境、种子、配置、日志和结果复算；
- 正文应说明实现语义、输入输出、验证和关键结果，让评委不运行代码也能审查模型链；
- 25 页以外仅 `Report on Use of AI` 享有官方明确的不计页数例外，不能把普通代码附录转移到该报告；
- 使用 AI 辅助代码时，正文内说明工具及用途并引用，AI 报告中记录使用过程，代码仍须手算小例、
  边界/不变量、基线、多初值或多种子核验。

这是一项提交格式约束，不代表代码可复现性不重要，也不证明“代码越少越容易获奖”。
